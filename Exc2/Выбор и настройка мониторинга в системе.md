## Основные проблемы, которые выявлены в системе и требуют мониторинга

1. Заказы теряются или обрабатываются с задержкой
2. Система API перегружена
3. MES и CRM работают медленно

## Мотивация

Почему в систему нужно добавить мониторинг и что это даст компании?

### 📌 1. Сокращение времени реакции на проблемы

Сейчас сбои в системе обнаруживаются от клиентов, как результат - недовольство, потери заказов.
С мониторингом можно увидеть проблему раньше, чем она скажется на бизнесе.

### 📌 2. Устранение потерь заказов

RabbitMQ — точка отказа. Если не отслеживать очереди, сообщения могут теряться.
Мониторинг позволит увидеть зависшие заказы и автоматически их восстановить.

### 📌 3. Ускорение работы API и БД

Сейчас непонятно, какие запросы самые медленные.
С помощью мониторинга можно оптимизировать производительность API и базы данных.

### 📌 4. Улучшение пользовательского опыта

Операторы жалуются на медленный MES, но нет данных, почему так происходит.
Мониторинг фронтенда поможет найти узкие места и улучшить интерфейс.

### 📌 5. Готовность к росту заказов

Без мониторинга компания не сможет предсказать, когда инфраструктура начнёт «ломаться».
С метриками можно заранее масштабировать API и базы, а не ждать, пока всё упадёт.

## Для разных частей системы Jewelry Store System можно использовать разные подходы к мониторингу.

### 🎯 RED (Requests, Errors, Duration) – можно использовать для мониторинга API

✅ Где использовать?
Shop API, CRM API, MES API – так как они обрабатывают HTTP-запросы.

✅ Какие метрики отслеживать?
🔹 Requests – сколько запросов поступает в API?
🔹 Errors – сколько запросов завершается с кодами 4xx и 5xx?
🔹 Duration – сколько времени занимает обработка запросов?

✅ Что это даст?
Быстрое выявление проблем с API (медленные запросы, рост ошибок).
Возможность масштабировать API, если RPS (запросов в секунду) растёт.

✅ Как реализовать?
Инструменты: Prometheus + Grafana, API Gateway (Kong, Nginx).
Логирование ошибок в Loki/ELK.

### 🎯 USE (Utilization, Saturation, Errors) – для баз данных и серверов

✅ Где использовать?
Базы данных (PostgreSQL, S3-хранилище 3D-файлов) – так как они могут перегружаться.

✅ Какие метрики отслеживать?
🔹 Utilization (загруженность) – % использования CPU, RAM, диска.
🔹 Saturation (перегрузка) – кол-во активных соединений к БД
🔹 Errors (ошибки) – запросы, завершающиеся таймаутами или отказами.

✅ Что это даст?
Позволит предсказать, когда база данных начнёт тормозить.

✅ Как реализовать?
PostgreSQL Exporter для мониторинга нагрузки на БД.

### 🎯 Четыре золотых сигнала – для RabbitMQ и пользователей

✅ Где использовать?

Очереди сообщений (RabbitMQ) – чтобы отслеживать задержку сообщений.
MES-дашборд операторов – для мониторинга пользовательского опыта.

✅ Какие метрики отслеживать?
🔹 Latency (задержка сообщений в RabbitMQ) – время от отправки до обработки.
🔹 Traffic (количество заказов в обработке) – сколько сообщений проходит через очередь?
🔹 Errors (потерянные сообщения) – сколько сообщений попало в DLQ (Dead Letter Queue в RabbitMQ)?
🔹 Saturation (перегрузка дашборда операторов) – время загрузки страниц MES.

✅ Что это даст?
Позволит выявлять застрявшие заказы и проблемы с обработкой сообщений.
Покажет, если интерфейс MES работает медленно.

✅ Как реализовать?
Grafana + Prometheus для анализа задержек в RabbitMQ.
Алерты, если средняя задержка сообщений > 3 мин или дашборд MES загружается > 5 сек.

Использование нескольких подходов позволит компании не только оперативно выявлять сбои, но и предотвращать проблемы до их возникновения.

## Метрики для мониторинга системы Jewelry Store System

### 1. Мониторинг RabbitMQ

📌 Number of dead-letter-exchange letters in RabbitMQ
✅ Позволяет выявить проблемы с обработкой сообщений: если письма попадают в DLQ, значит, есть сбой в потребителях очередей.
🟢 Ярлыки:

- Очередь (queue_name) – чтобы понимать, в какой именно очереди проблема.

📌 Number of messages in flight in RabbitMQ
✅ Если сообщений в обработке слишком много, это указывает на перегрузку RabbitMQ.
🟢 Ярлыки:

- Очередь (queue_name) – определяет, где именно проблема.

## 2. Мониторинг API (Shop API, CRM API, MES API)

### 📌 Number of requests (RPS) for Shop API, CRM API, MES API

✅ Позволяет отслеживать нагрузку на API и предсказывать моменты перегрузки.
🟢 Ярлыки:

- Тип запроса (request_type) – GET, POST, PUT, DELETE.
- Endpoint (endpoint_name) – чтобы видеть, какие API-запросы нагружают систему.

### 📌 Response time (latency) for Shop API, CRM API, MES API

✅ Если время ответа API растёт, это указывает на проблемы с производительностью.
🟢 Ярлыки:

- Endpoint (endpoint_name) – позволяет выявлять медленные запросы.

### 📌 Number of HTTP 500 for Shop API, CRM API, MES API

✅ Если растёт количество ошибок 500, значит, сервис работает нестабильно.
🟢 Ярлыки:

- Endpoint (endpoint_name) – помогает локализовать проблемные места.

### 📌 Number of simultanious sessions for Shop API, CRM API, MES API

✅ Позволяет понять, сколько пользователей одновременно работает с API.

## 3. Мониторинг серверов API (CPU, память)

### 📌 CPU % for Shop API, CRM API, MES API

✅ Рост загрузки CPU может указывать на утечки памяти или некорректную работу API.
🟢 Ярлыки:

- Instance ID (server_instance_id) – чтобы видеть, на каких серверах проблема.

### 📌 Memory Utilisation for Shop API, CRM API, MES API

✅ Позволяет определить, если API начинает потреблять слишком много памяти.
🟢 Ярлыки:

- Instance ID (server_instance_id) – для понимания, где именно перегрузка.

## 4. Мониторинг баз данных

### 📌 Memory Utilisation for Shop DB instance, MES DB instance

✅ Если память базы заполнена, она начинает тормозить, что приводит к задержкам.
🟢 Ярлыки:

- DB instance ID (db_instance_id) – чтобы видеть, где именно проблема.

### 📌 Number of connections for Shop DB instance, MES DB instance

✅ Позволяет выявить превышение лимита соединений с базой.
🟢 Ярлыки:

- DB instance ID (db_instance_id).

### 📌 Size of Shop DB instance, Size of MES DB instance

✅ Если размер БД растёт слишком быстро, это может привести к нехватке места.

## 5. Мониторинг хранилища S3 (3D-файлы)

### 📌 Size of S3 storage

✅ Позволяет контролировать, насколько быстро заполняется хранилище.

## 6. Мониторинг трафика API

### 📌 Kb transferred (received) for Shop API, CRM API, MES API

✅ Позволяет отслеживать нагрузку на сеть API.

### 📌 Kb provided (sent) for Shop API, CRM API, MES API

## Раздел «План действий» (драфт технического задания)

Для внедрения системы мониторинга Jewelry Store System необходимо выполнить следующие шаги.

### Этап 1: Развертывание инфраструктуры для мониторинга

📌 1.1. Развернуть time-series базу данных для хранения метрик. Использовать Prometheus как основную систему сбора и хранения метрик.
📌 1.2. Развернуть визуализацию метрик. Поднять Grafana для отображения данных Prometheus.
📌 1.3. Развернуть систему логирования. Установить Loki или ELK Stack для централизованного хранения логов.

### Этап 2: Настройка мониторинга API (Shop API, CRM API, MES API)

📌 2.1 Интеграция API с Prometheus. Добавить Prometheus Exporter в API для сбора метрик.
📌 2.2. Настроить мониторинг API Gateway. Добавить Kong (или Nginx) для балансировки API.
📌 2.3. Настроить алерты по API. Создать алерты в AlertManager, например, HTTP 500 > 1% запросов за 5 минут, Response time P99 > 500 мс, количество активных соединений API > 90% лимита.

### Этап 3: Мониторинг RabbitMQ и очередей сообщений

📌 3.1. Развернуть RabbitMQ Exporter. Установить RabbitMQ Prometheus Exporter для сбора метрик.
📌 3.2. Настроить алерты по RabbitMQ. Cоздать оповещения в Slack / Telegram

### Этап 4: Мониторинг баз данных (PostgreSQL, S3-хранилища)

📌 4.1. Развернуть мониторинг баз данных. Настроить сбор USE-метрик (Utilization, Saturation, Errors).
📌 4.2. Настроить алерты по БД

### Этап 5: Мониторинг пользовательского опыта и фронтенда

📌 5.1. Настроить мониторинг MES-дашборда операторов
📌 5.2. Оптимизировать логику обновления дашборда, например, внедрить WebSockets или GraphQL для обновления списка заказов.

### Этап 6: Автоматизация тестирования и CI/CD

📌 6.1. Добавить тестирование производительности API. Включить тестирование в CI/CD пайплайн.
📌 6.2. Внедрить канареечный деплой. Добавить blue-green deployment для безопасного обновления API.

## Определение показателей насыщенности и действий при превышении порогов

Показатели насыщенности определяют, насколько система загружена и в какой момент необходимо предпринимать действия, чтобы предотвратить сбои.

### 1. RabbitMQ: Количество сообщений в очереди в обработке (Number of messages in flight)

✅ Порог насыщенности:

- Критическое значение: 10 000 сообщений в одной очереди
- Предупреждающее значение: 5 000 сообщений в одной очереди

Если очередь RabbitMQ переполнена, это значит, что система не справляется с обработкой заказов.
Если сообщения задерживаются более 3 минут, клиенты начинают жаловаться.

✅ Что делать, если порог превышен?
🔴 (Критическое) 10 000+ сообщений в очереди:

- Завести аварийный тикет в Slack / Jira для команды DevOps.
- Добавить потребителей RabbitMQ (автоматически через авто-скейлинг).
- Уведомить ответственного инженера по мониторингу.
- Включить приоритетную обработку сообщений в очереди (если возможно).

🟡 (Предупреждение) 5 000 сообщений:

- Отправить уведомление в Telegram-канал мониторинга.
- Провести авто-диагностику задержек и записать лог причины (долго ли отвечают MES / CRM?).

### 2. API: Время ответа (Response Time P99)

✅ Порог насыщенности:

- Критическое значение: 1 секунда (P99)
- Предупреждающее значение: 500 мс (P99)

✅ Почему такие значения?

Клиенты ожидают быстрых ответов. Если API долго отвечает, это перегружает систему дополнительными запросами от клиентов (retries).

✅ Что делать, если порог превышен?
🔴 (Критическое) P99 > 1 сек:

- Завести аварийный тикет в Jira и уведомить DevOps.
- Включить авто-скейлинг API-инстансов (добавить новый сервер).
- Временно снизить лимиты rate-limiting (чтобы API не перегружали).

🟡 (Предупреждение) P99 > 500 мс:

- Уведомить в Slack / Telegram команду backend-разработчиков.
- Провести анализ зависших SQL-запросов в базе данных API.

### 3. База данных: Количество соединений (Number of connections for Shop DB, MES DB)

✅ Порог насыщенности:

- Критическое значение: 90% от максимального лимита соединений
- Предупреждающее значение: 75% от максимального лимита соединений

✅ Почему такие значения?
Если соединений слишком много, база начнёт отказывать новым запросам. Это приведёт к сбоям в API и задержке обработки заказов.

✅ Что делать, если порог превышен?
🔴 (Критическое) 90% от лимита:

- Добавить реплику базы данных (если возможно, автоматически).
- Перезапустить соединения с базой (убить зависшие запросы).
- Завести аварийный тикет в Jira.

🟡 (Предупреждение) 75% от лимита:

- Уведомить DevOps в Slack / Telegram.
- Включить логирование самых медленных SQL-запросов.
