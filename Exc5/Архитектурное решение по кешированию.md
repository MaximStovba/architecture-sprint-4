## Анализ проблемы с производительностью MES в системе «Александрит» и решение с кешированием

Oператоры жалуются на низкую скорость работы MES, а клиенты — на медленное выполнение заказов. Это может быть связано с несколькими факторами:

- **Долгие запросы к базе данных MESDB**
- **Высокая нагрузка на API MES**

✅ Основные кандидаты для кеширования:

- MES API

## Мотивация

В системе «Александрит» возникли проблемы с производительностью на уровне MES API и UI, что негативно влияет на работу операторов и скорость выполнения заказов. Внедрение кеширования поможет оптимизировать обработку данных и снизить нагрузку на базу данных и API, тем самым улучшив работу системы.

### Какие проблемы должно решить кеширование?

1. **Медленная загрузка страницы MES для операторов**.
2. **Долгое получение информации о статусе заказов**.

## Предлагаемое решение

В системе «Александрит» мы будем внедрять **серверное кеширование**, так как:

- **Клиентское кеширование** подходит только для статических ресурсов (изображения, CSS, JavaScript, 3D-модели), но не поможет ускорить сложные API-запросы и операции с заказами.
- **Серверное кеширование** позволяет кешировать динамические данные (списки заказов, статусы заказов, истории покупок) и снижает нагрузку на базу данных.

### В зависимости от типа данных, которые мы кешируем, используются разные паттерны кеширования:

- **MES API (список заказов)**. Тип данных - часто запрашиваемые, редко изменяемые. Паттерн кеширования - **Cache-Aside**. Заказы не меняются каждую секунду, но часто запрашиваются. Обновляем кеш раз в 5 минут. 💡 Паттерн Cache-Aside лучше всего подходит для приложений с большим объёмом запросов на чтение: ведь именно чтение оптимизируется в рамках этой стратегии.
- **MES API (статусы заказов)**. Тип данных - Часто запрашиваемые, динамичные. Паттерн кеширования - **Write-Through**. Сразу записываем данные в кеш, чтобы они были актуальны.

✅ Write-Through (для статусов) и Cache-Aside (для списка заказов) — лучший вариант 🚀.
❌ Read-Through не подходит, потому что:

- Он возвращает устаревшие данные, что критично для MES API.
- Не умеет эффективно кешировать динамические списки заказов.
- Создаёт избыточные записи в кеше, заполняя его ненужными данными.

## Oписание стратегии инвалидации кеша для MES API

1. **MES API (список заказов) — Cache-Aside + TTL**
   ✅ Почему Cache-Aside?

- Список заказов часто запрашивается, но редко изменяется.
- Запрос к БД можно избежать, если данные уже есть в кеше.
- Если заказа нет в кеше, API загружает его из БД и добавляет в кеш.

🔄 Инвалидация кеша:

- Автоматическая очистка по TTL (5 минут).
- Если данные в кеше устарели, их снова загружают из БД.

💡 Как избежать устаревших данных? Добавить программную инвалидацию: если в базе появился новый заказ → можно сбросить кеш вручную.

2. **MES API (статусы заказов) — Write-Through**
   ✅ Почему Write-Through?

- Статусы заказов часто меняются.
- Кеш должен быть всегда актуальным, иначе операторы увидят устаревший статус.
- Обновление сразу пишется в кеш и в БД.

  🔄 Инвалидация кеша:

- Кеш обновляется при каждом изменении статуса заказа.
- Кеш никогда не содержит устаревших данных, так как всегда синхронизирован с БД.
- Есть минусы: нагрузка на кеш больше, потому что любое изменение обновляет данные в Redis. Если кеш упадёт, запись в БД все равно произойдет, но кеш будет пустым и при следующем запросе понадобится обращаться к БД.

💡 Как избежать перегрузки кеша? Можно отключить кеширование для неактивных заказов, чтобы Redis хранил только статусы активных заказов.
